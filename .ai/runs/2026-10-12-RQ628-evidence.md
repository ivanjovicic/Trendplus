## Finding

- `TrendplusDbContext` maps `ProdajaStavka.PurchaseCostProvenance` to `prodaja_stavke.purchase_cost_provenance`.
- The field is queried by Supplier, Shoe Type and Color sales, as well as Insight Studio, Supplier Decision Hub, detail/cost snapshot and data-quality readers. The same absent column can therefore fail several analytics screens.
- The EF migration `20261010160000_AddPurchaseCostProvenance` and full core bootstrap already add the nullable column. However, `EnsureTrendplusCoreSchemaAsync` skips the full bootstrap when core tables are present. If migration history is ahead of the physical schema, `MigrateAsync` skips the already-recorded migration and previously allowed initialization to complete.
- The supplied incident proves PostgreSQL `42703` in Shoe Type, but does not show the production database migration history. That exact remote state is unverified.

## Follow-up audit: schema contract, RQ453 and Access import (2026-10-12)

### Verified cause and scope

- The supplied production error is PostgreSQL `42703` for `p.purchase_cost_provenance` on Shoe Type analytics. Supplier and Color analytics share the same mapped field; other provenance readers can also fail on a missing physical column. The exact production migration history and current schema were not queried, so the incident remains **unverified in production**.
- RQ453 CI run `38225927035` (run 854), job `114733299400`, failed at `2026-10-12T08:51:42Z`: supplier analytics returned HTTP 503 `starting/db_warmup` immediately after `CreateClient()`. The previous green run on PR #123 used `GateApiTraffic=false`, so it does not qualify as proof that the gated route is ready.

### Follow-up implementation in review

- `PurchaseCostProvenanceSchemaContract` defines the physical PostgreSQL contract as nullable `character varying(64)`, validates via PostgreSQL schema metadata, and keeps DDL in the explicit initializer only.
- `DatabaseInitializer` now verifies the full type/length/nullability contract after migration and additive repair. Bootstrap lifecycle coverage adds the migration-history-present/column-missing case, checks the expected pre-repair `42703`, preserves the existing `nabavna_cena`, exercises EF insert/read materialization, detects wrong type/nullability, and checks concurrent initializer calls under the existing advisory lock. It also asserts that the additive DDL fails under a read-only PostgreSQL connection rather than bypassing the configuration boundary.
- With automatic initialization disabled, the real readiness hosted service performs read-only schema validation on `DefaultConnection`, which backs the Supplier, Shoe Type and Color endpoints. It continues connectivity probes for both configured DBs. A contract mismatch is terminal (`/ready.status=failed`, failure category/stage included), and API traffic remains gated. The readiness PostgreSQL tests assert both fail-closed/no-DDL and healthy valid-schema outcomes.
- The RQ453 cross-screen tests now keep the traffic gate enabled, wait up to 180 seconds for actual `/ready` plus successful live DB probes, fail immediately on terminal startup/schema failure, and include the last status/body on timeout. The bound covers the current worst case of 12 attempts with two 5-second probes and 5-second delays (175 seconds) plus scheduling margin; the observed CI warmup interval was 12 seconds. No test is skipped or expected result weakened.

### Access import batch 43

- Code-path review found the Trendplus import writes and repeated `FlushTrendWritesAsync` saves are inside one `RetriableDbContextTransaction`; the transaction commits after the import work completes and rolls back on failure. The reported `42703` is non-transient, so the EF transient execution strategy should not replay it. The batch status/counters are maintained outside the sales transaction and counters can reflect attempted work.
- This supports rollback of the Trendplus sales rows for that failed attempt, but does not prove batch 43's exact terminal status, source file identity, target database or any external side effects. No production batch was inspected or rerun. Before an operator considers retry: verify the target via `current_database()`, `current_user`, server address/port and the runtime's effective connection configuration; confirm `DataImportBatches` shows batch 43 terminally failed (not queued/running), capture its source file/hash and failure details, and verify no committed rows for that source identity. Then apply/verify the schema using the separately approved deployment procedure, recheck readiness and analytics SELECTs, and only then have the owner explicitly authorize one controlled retry against the same source. Do not infer safety from `RetryCount` or attempted row counters.
