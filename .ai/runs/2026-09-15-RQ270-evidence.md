## Interpreted Outcome and Owner

**Owner**: Analytics Frontend / Inventory  
**Outcome**: Inventory page listens for and responds to `trendplus:data-scope-changed` events by reloading all primary (balance, list, insights) and signal (forecast, alerts, rebalance) panels as one coherent generation.

## Working Hypothesis

The header broadcasts `trendplus:data-scope-changed` when the global data scope changes (all → existing → imported). The Inventory page has no listener for this event, so its panels continue showing the previous scope's data until manual refresh or navigation.

**Solution**: Add a `useEffect` hook that listens for the event and increments `reloadNonce`, which is already a dependency of the main data-loading effect. This ensures all panels reload together in a single generation and respects existing request-sequence guards.

## Residual Risks

1. **Manual browser/scope-change proof**: This change assumes the header event system works as implemented. A human would need to:
   - Load Inventory page
   - Change global data scope via header
   - Verify all panels reload with new scope data
   - Verify detail modal state is preserved (per RQ203)

2. **Stale cache entries**: If an analytics request is in-flight when scope changes, the new request generation will not be affected (guarded by sequence numbers). However, a user who rapidly changes scopes during slow network conditions could see partial or delayed updates. This is acceptable per prompt design (request-sequence guards are intentional).

3. **Signal panel timing**: Forecast, alerts, and rebalance panels load asynchronously after primary panels. A very fast scope change might cause them to be requested after the reload trigger but before the primary panels have settled. The existing logic handles this (shouldRefreshSignals check), but real-world race-free behavior requires backend response coordination.
